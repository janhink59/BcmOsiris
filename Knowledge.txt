2. Databázové konvence (MSSQL)
* Databáze plně podporuje UTF-8 (zohledni to v PHP skriptech i T-SQL).
* Textové sloupce používají varchar/varchar(max), identifikátory používají typ uuid (uniqueidentifier). Názvy se píší striktně malými písmeny (snake_case).
* Změny struktur se provádí výhradně idempotentně: nové sloupce voláním EXEC p_create_missing_column, indexy voláním EXEC sp_create_index. U metadat a systémových tabulek (pokud ještě neobsahují uživatelská data a chybí v nich nový sloupec) je povolen bezpečný DROP.
* Je přísně zakázáno používat destruktivní DROP TABLE IF EXISTS u tabulek pro zachování existujících dat, pokud nejde o výše uvedenou výjimku.
* Cizí klíče (FOREIGN KEY) jsou zakázány, veškerá referenční integrita se řeší aplikačně nebo triggery. Oddělovač GO musí být vždy psán velkými písmeny.

3. Architektura RAC a SSC (Record & Access Control + Schvalovací cyklus)
* Záznamy jsou logicky identifikovány pomocí sloupce original (uuid). Primárním klíčem řádku je uuid.
* Vlastníkem (tenantem) je object_owner. Systémové záznamy mají object_owner = 0x00. Objekty vlastněné systémem nelze běžně smazat, k jejich deaktivaci slouží příznak inactive.
* Ochrana systémových metadat: Jakékoliv skripty, updaty a uložené procedury (např. p_fix_meta_column) modifikující sdílená metadata systému musí aplikovat striktní podmínku "object_owner = 0x00", aby se zabránilo destrukci a přepsání platných tenant overridů.
* Deterministický originál a Triggery: Vazební tabulky a další objekty používají deterministický hash pro sloupec original, aby se zabránilo duplicitám logických vazeb. Generuje se automaticky po insertu pomocí triggerů (prefix trgo_), které se dynamicky skládají na základě definice v jediné centralizované tabulce "meta_original_keys" (jeden řádek pro tabulku, definuje key1_column a key2_column). K výpočtu se využívá funkce f_generate_original. U aktivních primárních záznamů platí striktně pravidlo uuid = original. Záznamy přepsané tenantem dědí original ze své předlohy.
  - Triggery musí reagovat na AFTER INSERT, UPDATE pro podporu manuálních oprav dat.
  - V generátoru triggerů je nutné klíčové sloupce přetypovat přes CAST(... AS VARCHAR(MAX)), aby nedocházelo k pádům při implicitní konverzi.
  - Uvnitř triggeru musí klauzule LEFT JOIN parent obsahovat podmínku (parent.uuid <> i.uuid), aby se vkládaný systémový záznam nespároval sám se sebou.
* Výpočet v T-SQL: Při programatickém vkládání fixních systémových dat (např. v p_fix_meta_column) je žádoucí počítat deterministické original UUID rovnou funkcí dbo.f_generate_original přímo v T-SQL kódu, což eliminuje složité načítání hodnot přepsaných triggery.
* Klientský override (Views): Generovaná view (vrepo_{tabname}) automaticky skládají prioritu dat (tenant override > system). Poskytují sloupce:
  - {colname}: finální zresolvovaná hodnota.
  - {colname}_system: původní systémová hodnota 'A' záznamu pro zjištění odchylky.
  - {colname}_translated: systémový překlad pro aktuální jazyk 'L' (pouze pro překladatelné texty).
  - {colname}_original: 'A' záznam organizace, nebo systémový 'A' záznam (pouze pro překladatelné texty).
  - object_is_mine: příznak (1/0), zda tenant záznam přepsal.
* Ochrana systémových objektů a metadat: Tabulky využívají sloupce is_final a is_protected k řízení limitů klientského overridu:
  - is_final (bit): 1 = Zcela zakazuje organizacím (tenantům) vytvořit si vlastní přepis záznamu (typ 'A'). Povoluje pouze úpravu jazykových překladů (typ 'L').
  - is_protected (bit): 1 = Povoluje organizaci vytvořit vlastní přepis záznamu (typ 'A'), ale omezuje editaci v PHP výhradně na vizuální/prezentační vlastnosti. Technická logika zůstává readonly.
  - Metadatové sloupce jako "description", "helptext" atd. mohou být NULL, pokud dědí z předka (ancestor).
* Typy záznamů (record_type): 'A' = aktuálně schválený, 'L' = platná jazyková verze, 'H' = historický záznam (výhradně pro audit).
* Koncepty v SSC (vlastněné uživatelem): 'I' (Insert), 'U' (Update), 'D' (Delete), 'G' (úprava jazykové verze).
* Stavy schvalování (approval_status): Povolené hodnoty řídící SSC jsou 'D', 'W', 'S', 'A', 'R', 'C', 'I'.
* Povinné auditní sloupce jsou date_created, who_created, date_modified, who_modified, language, removed, valid_from, valid_to. Veškeré auditní vazby na uživatele využívají výhradně odkazy typu uuid.

4. Zpracování identit, SSO a multi-tenancy
* Tabulka user_account je globální (object_owner = 0x00). Přihlašovací jméno a e-mail musí být celosystémově unikátní.
* Přístup globálních uživatelů do konkrétních tenantů řídí vazební tabulka user_organization_access. View v_user_organization_access (s LEFT JOIN na dbsession) sjednocuje čtení oprávnění pro prvotní přihlášení i změnu kontextu.
* Volitelná role: Role v rámci tenanta se pamatuje ve sloupci last_orgadmin. Uživatel s právy administrátora (is_orgadmin = 1) si může při změně kontextu vybrat, zda do organizace vstoupí jako Administrátor nebo běžný Uživatel.
* AUTONOMNÍ AUDITNÍ STOPA: Tabulky relací (wwwsession, dbsession) obsahují sloupec user_access_uuid, který nese informaci o přístupové vazbě. Uložené procedury zapisující auditní stopy nesmí přijímat tyto hodnoty jako parametr z PHP. Procedura si musí vždy načíst hodnotu user_access_uuid přímo z tabulky dbsession podle aktuálního @@SPID. To samé platí pro ověřování ochrany proti smazání vlastního účtu.
* SSO integrace a autentizace probíhá plně v PHP vrstvě. Webový server má povolen anonymní přístup. Relaci zakládá p_set_login s ohledem na vyžádanou (@requested_org) či poslední navštívenou organizaci (zapisuje do dbsession / wwwsession).
* Přepínání kontextu uživatele (organizace, role) minimalizuje zátěž databáze: řídí se statickým příznakem change_context_allowed. V UI se organizace přepíná výhradně přes dedikovanou stránku (page_change_user_context) s využitím PRG vzoru.
* Pomocná ladicí relace se zakládá přes proceduru p_debuglogin.
* Bezpečnost účtů: Skripty a procedury musí obsahovat hard-coded override (čtením identity z dbsession), aby uživatel nemohl zrušit svá práva nebo deaktivovat sám sebe. Globální zablokování smí provést pouze sysadmin, lokální odebrání provádí orgadmin.
* HTTP hlavičky (autoredirect) musí být zasílány jako kompletní string (např. "Location: ...").

5. Architektura UI komponent a kódování stránek
* Abstraktní třídy komponent a základní stavební kameny jsou uloženy s prefixem abstract_. Nové stránky dědí z abstract_page a implementují metodu render_body().
* Tělo stránky (body) má zrušené okraje (margin a padding 0), aby se na něj mohl fixovat obsah bez rušivých mezer.
* Prvek abstract_page_master_detail zajišťuje dynamický dvoupanelový layout přes flexbox s nezávislými V-scrollbary. Podporuje asynchronní refresh levého panelu (ajax_panel=master) a nativní Fetch API.
* Klientský frontend využívá výhradně čistý (vanilla) JavaScript (ES6+). Je striktně zakázáno používat jQuery, jQuery UI nebo rozsáhlé frontendové frameworky.
* Formuláře musí být pro dokonalé zarovnání sloučeny do jedné HTML tabulky s využitím sjednocených CSS tříd (.md-table, .md-row-active, .md-row-inactive).
* Jmenná konvence stránek je page_{$page}.php a databázové procedury mají názvy page_{$page} a form_{$page}.
* Procedura page_{$page} dodává na stránku data (parametr @subpage určuje načítanou část).
* Procedura form_{$page} slouží k zápisu (parametr @subform specifikuje operaci).
* Router v index.php podporuje hybridní běh a autoloader se stará o načítání tříd.
* Globální uživatelský kontext zajišťuje třída user_context implementující __toString(), oddělující navigaci a session kontext.
* Veškeré zpracování POST dat, přesměrování (PRG) a definice UI polí (pageitem) probíhá v konstruktoru třídy stránky (před vykreslováním). Data se z databáze přenáší výhradně procedurami.
* Výchozí rozcestník po přihlášení je trvale page_main.php.
