2. Databázové konvence (MSSQL)
* Databáze plně podporuje UTF-8 (zohledni to v PHP skriptech i T-SQL).
* Textové sloupce používají varchar/varchar(max), identifikátory používají typ uuid (uniqueidentifier). Názvy se píší striktně malými písmeny (snake_case).
* Změny struktur se provádí výhradně idempotentně: nové sloupce voláním EXEC p_create_missing_column, indexy voláním EXEC sp_create_index.
* Je přísně zakázáno používat destruktivní DROP TABLE IF EXISTS u tabulek pro zachování existujících dat.
* Cizí klíče (FOREIGN KEY) jsou zakázány, veškerá referenční integrita se řeší aplikačně nebo triggery. Oddělovač GO musí být vždy psán velkými písmeny.

3. Architektura RAC a SSC (Record & Access Control + Schvalovací cyklus)
* Záznamy jsou logicky identifikovány pomocí sloupce original (uuid). Primárním klíčem řádku je uuid.
* Vlastníkem (tenantem) je object_owner. Systémové záznamy mají object_owner = 0x00. Objekty vlastněné systémem nelze běžně smazat, k jejich deaktivaci slouží příznak inactive.
* Klientský override (Views): Generovaná view (vrepo_{tabname}) automaticky skládají prioritu dat (tenant override > system). Poskytují sloupce:
  - {colname}: finální zresolvovaná hodnota.
  - {colname}_system: vždy původní systémová hodnota 'A' záznamu (dostupné pro VŠECHNY byznysové sloupce pro možnost zjištění odchylky v UI).
  - {colname}_translated: systémový překlad pro aktuální jazyk 'L' (pouze pro překladatelné texty).
  - {colname}_original: 'A' záznam organizace, nebo systémový 'A' záznam (pouze pro překladatelné texty).
  - object_is_mine: příznak (1/0), zda tenant záznam přepsal.
* Typy záznamů (record_type): 'A' = aktuálně schválený, 'L' = platná jazyková verze, 'H' = historický záznam (výhradně pro audit).
* Koncepty v SSC (vlastněné uživatelem): 'I' (Insert), 'U' (Update), 'D' (Delete), 'G' (úprava jazykové verze).
* Stavy schvalování (approval_status): Povolené hodnoty řídící SSC jsou 'D', 'W', 'S', 'A', 'R', 'C', 'I'.
* Povinné auditní sloupce jsou date_created, who_created, date_modified, who_modified, language, removed, valid_from, valid_to. Veškeré auditní vazby na uživatele využívají výhradně odkazy typu uuid.

4. Zpracování identit, SSO a multi-tenancy
* Tabulka user_account je globální (object_owner = 0x00). Přihlašovací jméno a e-mail musí být celosystémově unikátní.
* Přístup globálních uživatelů do konkrétních tenantů řídí vazební tabulka user_organization_access (obsahuje is_orgadmin a lokální removed). View `v_user_organization_access` (s LEFT JOIN na dbsession) sjednocuje čtení oprávnění pro prvotní přihlášení i změnu kontextu.
* SSO integrace a autentizace probíhá plně v PHP vrstvě. Webový server má povolen anonymní přístup. Relaci zakládá T-SQL procedura `p_set_login` s ohledem na vyžádanou (`@requested_org`) či poslední navštívenou organizaci (zapisuje do dbsession / wwwsession).
* Přepínání kontextu uživatele (organizace, role) minimalizuje zátěž databáze: řídí se statickým příznakem `change_context_allowed` (kalkulovaným v `p_set_login`) v tabulce relací. V UI se organizace nepřepíná roletkou v záhlaví, ale výhradně přes dedikovanou stránku (`page_change_user_context`) s využitím PRG vzoru a procedury `p_set_login`.
* Pomocná ladicí relace se zakládá přes proceduru `p_debuglogin` (využívající interně `p_set_login` a `p_init_wwwsession`).
* Bezpečnost účtů: Skripty i T-SQL procedury musí vždy obsahovat hard-coded override, aby uživatel nemohl zrušit svá práva nebo deaktivovat sám sebe. Globální zablokování (inactive) smí provést pouze sysadmin, lokální odebrání přístupu (removed) provádí orgadmin. Filtrování historických/odstraněných záznamů probíhá překreslením na backendu (SQL + PHP sessioninput), nikoliv skrýváním v UI.
* HTTP hlavičky (autoredirect) musí být zasílány jako kompletní string (např. "Location: ...").

5. Architektura UI komponent a kódování stránek
* Abstraktní třídy komponent a základní stavební kameny jsou uloženy s prefixem `abstract_` (např. `abstract_component.php`, `abstract_page.php`, `abstract_page_master_detail.php`). Nové stránky dědí z `abstract_page` a implementují metody `render_body()`.
* Tělo stránky (`body` v `abstract_page.php`) má zrušené okraje (margin a padding 0), aby se na něj mohl fixovat obsah bez rušivých mezer.
* Prvek `abstract_page_master_detail` zajišťuje dynamický dvoupanelový layout přes flexbox, s fixní responzivní výškou a oddělenými nezávislými V-scrollbary pro Master a Detail panel. Router v této třídě podporuje asynchronní refresh levého panelu přes URL parametr `ajax_panel=master`.
* Klientský frontend využívá výhradně čistý (vanilla) JavaScript (ES6+). Je striktně zakázáno používat jQuery, jQuery UI nebo rozsáhlé frontendové frameworky. Pro AJAX komunikaci se používá výhradně nativní Fetch API.
* Pro formuláře, tabulky a seznamy je zakázáno používat roztříštěné struktury a inline styly. Formulářová pole musí být pro dokonalé zarovnání sloučena do jedné HTML tabulky (sloupec label + sloupec hodnota). Varovné stavy a logické skupiny se odlišují podbarvením nebo vloženými hlavičkami přímo na úrovni řádků (`<tr>`). Využívají se sjednocené CSS třídy (`.md-table`, `.md-row-active`, `.md-row-inactive`).
* Router v `index.php` podporuje hybridní běh: u legacy stránek provede kód okamžitě přes `require_once`, u nových instanciuje třídu `page_{$page}` a volá metodu `render()`.
* Třídy jsou automaticky načítány pomocí nativního `spl_autoload_register` definovaného v `config.php`.
* Globální uživatelský kontext zajišťuje třída `user_context` implementující metodu `__toString()`. Zobrazuje se jako kompaktní, statický horizontální horní pruh obrazovky, s vyhrazeným prostorem pro grafiku vlevo a odhlášením vpravo.
* Veškeré zpracování POST dat, přesměrování (PRG) a definice UI polí (`pageitem`) probíhá v konstruktoru třídy stránky (nikoliv v metodách `render_*`), čímž je zaručeno, že hlavičky stránky a databázové stavy budou konzistentní před samotným vykreslováním HTML.
* Přenos dat z databáze do stránek a komponent se provádí výhradně voláním uložených procedur.
* Jmenná konvence stránek je `page_{$page}.php` a databázové procedury mají názvy `page_{$page}` a `form_{$page}`.
* Procedura `page_{$page}` dodává na stránku všechna potřebná data, prvním parametrem je @subpage, která určuje, která část stránky se má načíst (např. 'main','detail' atd.)
* Procedura `form_{$page}` s potřebnými parametry slouží k zápisu, zpravidla zpracování formulářů. Prvním parametrem je @subform, který specifikuje, o jakou operaci zápisu se jedná (stisknuté tlačítko apod.)
* Výchozí rozcestník po přihlášení je trvale `page_main.php`.

6. Stromové struktury, CRMM a Infrastruktura
* Sémantická struktura stromů se udržuje primárně přes relační vazbu parent_uuid. Textový sloupec sort_code slouží pouze pro rychlé třídění na frontendu, aby se zabránilo lavinovým updatům SSC při přesunech větví.
* Striktní pravidlo uzlů (is_leaf): Aktiva se smí vázat výhradně na koncové uzly (is_leaf = 1). Pokud klient pod systémový uzel přidá vlastní větev, ztráta statutu listu se musí dynamicky vyhodnocovat poddotazem ve View, nebo zajistit aplikační migrací aktiv.
* Výpočty CRMM: Zbytkové riziko se kalkuluje z hrubého rizika přes redukční a rizikový faktor napojených opatření. Logaritmické škálování hrozeb/zranitelností používá číselné skóre.
* Infrastruktura: Produkční prostředí na Windows Serveru vyžaduje stejnou úpravu registrů jako Windows 10 (LongPathsEnabled), aby mohl Composer správně instalovat obří závislosti.
